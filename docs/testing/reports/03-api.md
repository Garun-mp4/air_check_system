# Отчёт тестового блока 03 — серверный REST API и контракты данных

## Область проверки

Проверены route handlers и преобразование данных для:

- `POST /api/v1/measurements`;
- `GET /api/v1/measurements/latest`;
- `GET /api/v1/measurements/history`;
- `GET /api/v1/prediction/latest`;
- `GET /api/v1/recommendation`;
- `GET` и `PATCH /api/v1/settings`.

Также проверены парсеры telemetry, параметров истории, `device_id` и PATCH настроек. Включены HTTP-статусы, публичный JSON в snake_case, преобразование дат/offset, границы сенсорных значений, лимиты, ошибки и отсутствие вызова записи для невалидного payload.

Авторизация и проверка machine token замоканы и не являются предметом этого блока. Очередь команд, ACK и ML-клиент отдельно не тестировались. Route tests изолируют handlers от PostgreSQL и внешних сервисов; интеграция реальной БД в эту кампанию не входила.

## Что подтверждено

- Валидное telemetry payload преобразуется в внутренние числовые поля и `Date`; timezone offset нормализуется к UTC, значения и единицы не пересчитываются.
- Все документированные границы CO₂, температуры, влажности и PM2.5 включительны; нечисловые, не конечные, пропущенные и выходящие за границы значения отклоняются.
- Некорректный JSON и validation errors возвращают структурированный `400`; invalid telemetry не вызывает `ingest`, invalid settings patch не вызывает update.
- Успешный ingest возвращает `201`; измерения, прогнозы, рекомендации и настройки сериализуются в ожидаемые поля и ISO timestamps.
- История применяет настроенный default limit, принимает заданный диапазон и `limit=5000`, отклоняет перепутанные границы и некорректные лимиты.
- До появления записей latest/prediction/recommendation возвращают `data: null`; пустая история возвращает пустой `data` и `meta.count=0`.
- Settings PATCH сохраняет частичную семантику и преобразует snake_case полей к внутреннему camelCase.
- Неожиданная ошибка сервиса не раскрывает текст ошибки клиенту: handler возвращает общий `500 internal_error`.

## Вопросы и наблюдения для последующей доработки

1. **Политика неизвестного `device_id` не определена однозначно.** Миграции содержат `device_id` как текстовый ключ, отдельной таблицы/реестра устройств нет. Текущий settings route проверяет синтаксис идентификатора и передаёт его сервису; репозиторий создаёт настройки для отсутствующего ключа. Тест фиксирует это поведение, но не объявляет его ошибкой. Перед усилением тестов нужно решить, допустимы ли динамические узлы или разрешён только `DEVICE_ID` текущей установки.
2. **Формат времени стоит уточнить.** `docs/api.md` требует часовую зону; `validation.ts` сообщает RFC3339, но использует разбор JavaScript `Date` вместе с проверкой суффикса временной зоны. Тесты требуют timezone и отклоняют невалидные даты, не навязывая более строгую грамматику. Если API должен принимать только строгий RFC3339, это нужно явно закрепить в контракте.
3. **Telemetry POST не принимает `device_id`.** Это соответствует текущему контракту одного локального узла и текущему payload simulator. Если появятся несколько узлов в одном API, нужен отдельный контрактный этап, а не молчаливое добавление поля тестами.

## Границы и следующий шаг

Проверки выполнялись без живого PostgreSQL, ML-service или backend полного Compose-стенда. Поэтому они подтверждают преобразование и поведение handler-ов с подменёнными сервисами, но не транзакционность PostgreSQL и не сквозную обработку реальных сетевых ошибок. Не обнаружено невыполненных тестовых задач в пределах блока 03; найденные вопросы относятся к уточнению контракта и отдельной интеграционной проверке.
