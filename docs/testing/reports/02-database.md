# Отчёт по блоку 02: PostgreSQL, миграции и хранение данных

## Область проверки

Проверены миграции `001_init.sql`–`005_auth.sql`, ограничения и индексы PostgreSQL, а также фактический `PostgresRepository` из `frontend/src/server/repository.ts`. Production-код, SQL-миграции и существующие файлы не менялись.

Набор покрывает:

- применение миграций на пустой базе и повторный запуск поверх существующих данных;
- диапазоны измерений, граничные значения, внешние ключи, уникальность и каскадное удаление;
- роли доступа, ограничение единственного владельца и nullable-ссылки журнала аудита;
- индексы сортировки истории, очереди команд и retention;
- чтение/запись измерений, сортировку при одинаковых timestamp и границы истории;
- прогнозы, рекомендации и изолированные настройки узлов;
- retention-порог, сохранение ожидающих команд и состояния исполнительных устройств;
- транзакционный rollback при ошибке записи команд, ACK/actual state и очистки;
- параллельную запись измерений и дедупликацию одинаковых команд.

## Изолированное окружение

- Windows, Python 3.12.10, pytest 8.3.5.
- Docker Engine 29.6.1; PostgreSQL `16-alpine`, локальный image ID `sha256:cf78e76683b9ca8c5733cbbdce6c9262b45b6767934dd0a95e671f9a0fc20685`.
- Node.js 22.22.2, `pg` 8.23.0.
- Каждый прогон создаёт контейнер с уникальным именем и label `org.aircheck.test-scope`, опубликованным случайным localhost-портом и временным `tmpfs` на `/var/lib/postgresql/data`. Контейнер запускается напрямую через `docker run --rm`: Compose, `.env`, текущие контейнеры, именованные volumes и существующие БД не используются.
- Учетные данные генерируются на время теста, не записываются в файлы и скрыты из `repr` фикстуры. После каждого прогона проверяется ID и label контейнера, затем останавливается только он.
- Readiness проверяется через TCP на `127.0.0.1:5432` внутри временного контейнера; миграции также применяются через TCP. Это исключает ранний Unix-сокет временного init-процесса PostgreSQL.

Если Docker Engine недоступен, PostgreSQL-зависимые проверки помечаются pytest как `skipped`; статическая проверка имён миграций остаётся доступной. Для вызова TypeScript-репозитория нужны Node.js и зависимости `frontend` (`npm ci`).

## Найденная проблема приложения

`test_postgres_repository_concurrent_identical_commands_are_deduplicated` выявляет гонку в `PostgresRepository.queueControlCommands`:

1. Две транзакции одновременно читают одно и то же отсутствие ожидающей команды.
2. Обе проходят проверку `pendingForTarget` до фиксации другой транзакции.
3. Обе добавляют одну и ту же команду.

На чистых PostgreSQL-базах тест воспроизвёл 2 дубликата в двух отдельных повторных прогонах; без синхронизации конкурентного участка при более широком fan-out наблюдалось 4 вставки из 12 запросов. Тестовый барьер удерживает конкурирующие INSERT после чтения очереди, но ограниченно отпускает запрос, если реализация сериализует операции до INSERT. Поэтому он не требует ожидать тестовый барьер от корректно заблокированной реализации.

Для исправления требуется сериализовать постановку команд для одного `device_id` внутри транзакции — например, блокировкой строки соответствующего `actuator_states` через `SELECT ... FOR UPDATE` до чтения desired state и pending-команд. На момент исходного прогона production-код не менялся; текущий результат приведён ниже.

Других ошибок в проверенных миграциях, ограничениях, индексах, retention и транзакционном сохранении тесты не обнаружили.

## Ограничения охвата

- Тесты проверяют локальную модель PostgreSQL и репозиторий напрямую; сквозной HTTP/API/automation/ACK-путь относится к другим блокам карты тестирования.
- Нагрузочная производительность и поведение при обрыве сети не измерялись.
- Командная очередь проверена на дедупликацию одинакового желаемого состояния при конкуренции; весь бизнес-контракт автоматики и ACK остаётся в соответствующих блоках карты.

## Повторная проверка после исправления

В исходном прогоне строка `actuator_states` теперь блокируется через `SELECT ... FOR UPDATE` внутри транзакции до чтения состояния и pending-команд. Это сериализует одинаковые постановки для одного `device_id`; публичная политика дедупликации записана в `docs/api.md` и `docs/ТЗ-поправка-03-climate-control.md`.

После исправления `python -m pytest tests/database -q` завершился результатом **41 passed, 0 failed, 0 skipped**. Полный настроенный Python набор завершился результатом **262 passed, 0 failed, 4 skipped**; пропущенные проверки — только Compose E2E без opt-in. Конкурентная дедупликация входит в прошедшие 41 database-тест.
