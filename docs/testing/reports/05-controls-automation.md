# Блок 05 — управление климатом, автоматика и ACK

## Границы проверки

Новый набор находится в `frontend/src/server/control-service.test.ts`. Он вызывает настоящий `ControlService` и использует `MemoryRepository` как тестовую зависимость; в тестах нет сетевых вызовов и отдельных mocks для control-service.

Проверка проходит на уровне сервиса и in-memory репозитория. Она не запускает HTTP-маршруты, авторизацию, PostgreSQL или миграции. `frontend/src/server/server.test.ts` уже содержит релевантное покрытие того же сочетания сервиса/репозитория: пакетное управление, ACK, команды другого узла, устаревшие отчёты и основные циклы автоматики. Этот файл также включает тесты других серверных областей, поэтому он указан в полном релевантном прогоне, но не изменялся.

В качестве контракта сверены раздел управления в `docs/api.md`, поправка `docs/ТЗ-поправка-03-climate-control.md`, `control-service.ts`, `recommendation.ts`, `settings.ts`, обе реализации репозитория и миграции `002_controls.sql` и `004_node_settings.sql`.

## Новый набор

Добавлены проверки:

- одиночная ручная команда остаётся pending и последовательный повтор того же намерения не добавляет дубликат;
- длительность оконного override берётся из настроек узла, а действие `window=auto` снимает режим без новой моторной команды;
- после истечения override автоматика снова выдаёт команды;
- pending-команда повторно возвращается при опросе недоступного узла;
- критический прогноз создаёт одну автоматическую партию для окна, вытяжки и притока;
- настройки отключают автоматику целиком или только автоматическое управление окном;
- несовпадающее фактическое состояние не должно подтверждать команду.

В исходном прогоне последняя проверка оставлена падающей: это был подтверждённый дефект реализации, а не нестабильный тест. Исправление описано ниже.

## Подтверждённая проблема

Узел сообщает `exhaust_on=false` и включает ID pending-команды вытяжки с `desired_state=true`. Оба репозитория всё равно помечают команду `applied`, из-за чего она исчезает из очереди, хотя `reported` и `desired` расходятся. Это противоречит точному правилу API: ACK принимается, только если поле actual совпадает с `desired_state` (`docs/api.md`, раздел `POST /api/v1/controls/state`).

В `MemoryRepository.reportControlState` проверяются ID, узел и статус, но не значение актуального поля (`frontend/src/server/repository.ts`, строки 359–369). SQL в `PostgresRepository.reportControlState` также фильтрует по узлу, pending-статусу и перечисленным ID, но не сопоставляет target/`desired_state` с новым reported state (строки 957–965). Новый тест воспроизводит ошибку на `MemoryRepository`; SQL показывает ту же проблему в постоянной реализации. Production-код по условиям этапа не менялся.

Существующее покрытие подтвердило ожидаемое поведение для ACK команды того же узла, игнорирования ACK ID другого узла и отчёта с более старой временной меткой. Автоматические команды остаются pending без отчёта устройства.

## Открытые вопросы контракта

- Поправка к ТЗ говорит, что перечисленные ID после отчёта становятся `applied`, не уточняя совпадение состояния (`docs/ТЗ-поправка-03-climate-control.md`, раздел REST-контракта). `docs/api.md` формулирует более точное условие совпадения; новый тест следует ему и также соответствует заданию этого этапа. Нужно синхронизировать формулировки документов.
- Контракт не определяет обработку отчёта с временной меткой, равной последней. Текущие реализации его принимают; отдельное ожидание не закреплялось.
- Последовательное повторение одинаковой команды дедуплицируется реализацией. В публичном контракте не найдено обещания конкурентной идемпотентности или защиты гонок, поэтому параллельные запросы не тестировались.

## Что требовалось до исправления

Требовалось исправить ACK-переход в обеих реализациях репозитория: устанавливать `applied` только для перечисленных pending-команд того же узла, чьи target и `desired_state` соответствуют значению actual в отчёте, а затем повторно запустить Vitest-прогоны.

## Результат исправления

Обе реализации репозитория теперь сопоставляют `target` и `desired_state` со своим фактическим boolean-полем до перехода в `applied`. Отчёт с несовпадающим состоянием обновляет `reported`, но оставляет команду в очереди. Поправка к ТЗ приведена в соответствие с более точным правилом `docs/api.md`.

При повторной проверке найден устаревший существующий тест, который ожидал подтверждения сразу для команд `ON` и `OFF` при одном `reported=false`. Он противоречил контракту, поэтому его ожидание уточнено: команда `OFF` подтверждена, команда `ON` остаётся pending. Новые проверки покрывают mismatch для `exhaust`, `intake` и `window`.

Целевой набор `control-service.test.ts` + `server.test.ts`: **42 passed, 0 failed, 0 skipped**. PostgreSQL набор: **41 passed**, включая mismatch и matching ACK для всех трёх целей. E2E проверка полной автоматической партии в Compose повторно прошла.
