## Цель

Панель AirCheck должна не только отображать качество воздуха, но и управлять локальным климатическим контуром комнаты. Контур включает вытяжку для удаления старого воздуха, фильтрованный приток нового воздуха и автоматическое окно.

Физических устройств на текущем этапе нет. Поэтому simulator реализует поведение будущей ESP32, а сервер, база данных, API и интерфейс проектируются так, чтобы источник можно было заменить без изменения публичного контракта.

## Обязательное состояние

Для узла `DEVICE_ID` сервер хранит:

- фактическое состояние `reported`: `exhaust_on`, `intake_on`, `window_open`;
- желаемое состояние `desired` с теми же полями;
- `window_mode`: `auto` или `manual`;
- `override_until` для временной ручной блокировки окна;
- `window_open_since` для минимальной длительности проветривания;
- `last_reported_at` и вычисляемый статус `online`, `stale` или `offline`;
- очередь `actuator_commands` со статусом `pending/applied`, источником `manual/automatic`, причиной и `batch_id`.

Расхождение `desired` и `reported` означает, что команда ещё не подтверждена. Сервер не должен выдавать pending-команду за выполненную.

## REST-контракт

### Получение состояния

`GET /api/v1/controls?device_id=room-01` возвращает reported/desired, режим окна, доступность узла, количество pending-команд и последнюю команду.

### Ручная команда

`POST /api/v1/controls/commands`:

```json
{"device_id":"room-01","target":"exhaust","action":"on"}
```

Допустимые действия:

- `exhaust`: `on`, `off`;
- `intake`: `on`, `off`;
- `window`: `open`, `close`, `auto`.

`exhaust` и `intake` независимы и могут включаться одновременно. `window=open|close` устанавливает ручной override на `WINDOW_MANUAL_OVERRIDE_MINUTES`, а `window=auto` возвращает окно автоматике.

### Исполнение узлом

`GET /api/v1/controls/commands?device_id=room-01&limit=20` выдаёт pending-команды simulator/ESP32.

`POST /api/v1/controls/state` принимает подтверждение:

```json
{
  "device_id":"room-01",
  "timestamp":"2026-09-06T10:00:00Z",
  "exhaust_on":true,
  "intake_on":true,
  "window_open":true,
  "applied_command_ids":[101,102,103]
}
```

После запроса сервер обновляет reported и отмечает перечисленные команды как applied.

## Автоматика

После нового измерения и прогноза сервер:

1. при текущем или прогнозируемом CO₂ не ниже `CO2_CRITICAL_THRESHOLD` открывает окно и одновременно включает вытяжку и приток;
2. при открытом окне и CO₂ выше `CO2_NORMAL_THRESHOLD` поддерживает оба воздушных канала включёнными;
3. при CO₂ и прогнозе ниже нормального порога после `AUTO_VENTILATION_MINIMUM_MINUTES` закрывает окно и выключает оба канала;
4. не вмешивается в ручной режим окна до окончания override;
5. оставляет команду pending при недоступном устройстве.

Три действия одного автоматического цикла объединяются `batch_id`.

## UX

В панели должны быть:

- отдельные controls вытяжки и притока;
- явная подпись, что приток фильтрованный;
- индикация «включено/выключено», «ожидание устройства» и доступности узла;
- состояние окна «открыто/закрыто»;
- режимы «Авто», «Открыть», «Закрыть»;
- сообщение о временном ручном override;
- mobile-first layout с крупными tappable controls и без горизонтального скролла.

Тип физического механизма окна в UI не упоминается.

## Проверка готовности

Нужно проверить unit/integration-тестами и реальным локальным сценарием:

- ручное включение вытяжки;
- одновременное включение вытяжки и притока;
- открытие окна и временный override;
- автоматическое открытие по критическому CO₂/прогнозу;
- подтверждение команд simulator;
- автоматическое закрытие после снижения CO₂ и минимального времени;
- отображение reported/desired и pending-команд в API и панели.
