# REST/JSON API

Все endpoints TypeScript-сервера находятся в Next.js route handlers и работают относительно /api/v1.

## POST /api/v1/measurements

Входное тело:

~~~json
{
  "timestamp": "2026-09-06T10:00:00Z",
  "indoor": {
    "co2": 720,
    "temperature": 23.4,
    "humidity": 45,
    "pm25": 5.2
  },
  "outdoor": {
    "temperature": 18,
    "humidity": 60,
    "pm25": 8
  },
  "window_open": false
}
~~~

Дата должна содержать часовой пояс. Сервер проверяет типы, конечность и физически допустимые диапазоны значений, затем сохраняет запись в measurements. В ответе 201 возвращаются измерение, прогноз (если достаточно истории и ML-сервис доступен), рекомендация и prediction_status.

simulator отправляет именно это тело. Поэтому будущая ESP32 сможет заменить simulator без отдельного endpoint или преобразователя.

## GET /api/v1/measurements/latest

Ответ:

~~~json
{
  "data": {
    "measurement": {
      "id": 481,
      "created_at": "2026-09-06T10:00:00.100Z",
      "timestamp": "2026-09-06T10:00:00.000Z",
      "indoor": {"co2": 720, "temperature": 23.4, "humidity": 45, "pm25": 5.2},
      "outdoor": {"temperature": 18, "humidity": 60, "pm25": 8},
      "window_open": false
    },
    "prediction": null,
    "recommendation": null
  }
}
~~~

До первого измерения вложенные значения равны null. Это позволяет frontend показать штатное empty-state.

## Настройки узла

`GET /api/v1/settings?device_id=room-01` возвращает постоянные правила конкретного локального узла. `PATCH /api/v1/settings` обновляет одно или несколько полей:

~~~json
{
  "device_id": "room-01",
  "automation_enabled": true,
  "auto_window_enabled": true,
  "manual_override_minutes": 30,
  "auto_ventilation_minimum_minutes": 5,
  "co2_normal_threshold": 800,
  "co2_critical_threshold": 1000,
  "pm25_good_limit": 15,
  "pm25_elevated_limit": 35,
  "alerts_enabled": true
}
~~~

Сервер проверяет диапазоны и порядок порогов: критический CO₂ должен быть выше комфортного, а повышенный PM2.5 — выше нормального. Сохранённые значения применяются к автоматике, рекомендациям и шкалам показателей. `retention_hours` возвращается только для справки и не изменяется через этот endpoint.

## GET /api/v1/measurements/history

Параметры from и to — необязательные RFC3339 даты, limit — число от 1 до 5000. Ответ содержит data с измерениями в порядке возрастания времени и meta. Панель использует периоды 30 минут, 1 час, 6 часов и 24 часа.

## GET /api/v1/prediction/latest и GET /api/v1/recommendation

Возвращают { "data": ... }. До появления записи data равен null.

## Управление климатическим контуром

Управление рассчитано на одну локальную комнату и один узел, идентификатор которого задаётся `DEVICE_ID`. Сервер хранит два представления состояния:

- `reported` — последнее подтверждение от simulator/ESP32;
- `desired` — состояние, которое сервер ожидает от узла.

Пока эти состояния различаются, команда остаётся pending и frontend показывает ожидание устройства.

### GET /api/v1/controls

Возвращает актуальное состояние климатического контура. Необязательный параметр `device_id` позволяет явно выбрать узел.

```json
{
  "data": {
    "device_id": "room-01",
    "connection": {
      "status": "online",
      "last_seen_at": "2026-09-06T10:00:00Z"
    },
    "reported": {
      "exhaust_on": false,
      "intake_on": false,
      "window_open": false
    },
    "desired": {
      "exhaust_on": true,
      "intake_on": true,
      "window_open": true
    },
    "window": {
      "mode": "auto",
      "override_until": null,
      "open_since": null
    },
    "automation": {
      "enabled": true,
      "status": "waiting_for_device",
      "message": "Команда ожидает подтверждения локального узла."
    },
    "pending_commands": 3,
    "last_command": null,
    "updated_at": "2026-09-06T10:00:00Z"
  }
}
```

`connection.status` имеет значения `online`, `stale` или `offline`. Состояние окна дополнительно содержит `mode`: `auto` или `manual`.

### POST /api/v1/controls/commands

Создаёт ручную команду для узла. Тело запроса:

```json
{
  "device_id": "room-01",
  "target": "exhaust",
  "action": "on"
}
```

Допустимые комбинации:

- `target=exhaust`, `action=on|off` — вытяжка;
- `target=intake`, `action=on|off` — фильтрованный приток;
- `target=window`, `action=open|close|auto` — окно и снятие ручной блокировки.

Команды `exhaust` и `intake` независимы и могут быть включены одновременно. Для открытия/закрытия окна создаётся временная ручная блокировка на `WINDOW_MANUAL_OVERRIDE_MINUTES`; `auto` возвращает окно под контроль автоматики. Ответ на новую команду — `202 Accepted`, а для `window:auto` без изменения состояния — `200`.

Повторная постановка того же желаемого состояния для того же узла и цели не создаёт вторую запись, пока такая команда уже ожидает исполнения. Проверка и запись сериализуются по узлу, поэтому параллельные одинаковые запросы также дают одну pending-команду. Команда с другим целевым состоянием сохраняется как отдельное намерение.

### GET /api/v1/controls/commands

Возвращает pending-команды для simulator/ESP32:

```text
GET /api/v1/controls/commands?device_id=room-01&limit=20
```

Команды отсортированы по времени создания. В каждой записи есть `id`, `target`, `desired_state`, `source`, `reason`, `batch_id`, `status` и timestamps. Автоматическое открытие окна, включение вытяжки и включение притока объединяются одним `batch_id`.

### POST /api/v1/controls/state

Узел подтверждает фактические состояния одним запросом:

```json
{
  "device_id": "room-01",
  "timestamp": "2026-09-06T10:00:00Z",
  "exhaust_on": true,
  "intake_on": true,
  "window_open": true,
  "applied_command_ids": [101, 102, 103]
}
```

Сервер обновляет `reported`, сохраняет время последнего подтверждения и отмечает перечисленную pending-команду как `applied` только если её `desired_state` совпадает с соответствующим boolean-полем отчёта. При несовпадении команда остаётся pending для повторной синхронизации. Пока для цели есть pending-команда, сервер сохраняет её `desired_state`. Если pending-команды для цели нет, актуальный `reported` от устройства также становится текущим `desired_state`: это не оставляет панель в вечном ожидании после перезапуска узла или физического изменения состояния. Фактическое состояние устройства остаётся источником истины. Simulator и будущая ESP32 используют один и тот же контракт.

## Ошибки

~~~json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте данные запроса",
    "fields": [
      {"field": "window_open", "message": "должно быть boolean"}
    ]
  }
}
~~~

Ошибки базы и внешнего сервиса не раскрывают внутренние детали SQL. Ошибка ML-прогноза не отменяет сохранение измерения.

## Жизненный цикл команд (M1)

Команда переходит из `pending` ровно в одно конечное состояние: `applied`, `failed`, `cancelled` или `expired`. Возврат к `pending` не допускается. Ручная команда действует 5 минут, автоматическая — 2 минуты с момента создания сервером. Поля `expires_at`, `completed_at`, `failure_reason` дополняют прежний контракт; `applied_at` сохраняется для совместимости.

Выдача очереди, получение состояния и обработка отчёта сначала завершают истекшие команды. ACK принимается только для неистекшей `pending` команды своего узла с совпадающим фактическим состоянием цели. Поздний или повторный ACK не меняет конечный статус, но свежий отчёт по-прежнему обновляет фактическое состояние. Противоположная новая команда отменяет прежнюю ожидающую команду той же цели. Очередь, ACK и отмена сериализуются блокировкой строки узла в PostgreSQL.

Отчёт устройства может дополнительно содержать `failed_commands: [{"id": 123, "reason": "Мотор заблокирован"}]`. Причина — непустая строка до 500 символов; не более 100 уникальных ошибок и 100 уникальных ACK. Один id нельзя одновременно подтверждать и отклонять. Старые устройства продолжают отправлять `applied_command_ids` без нового поля.

`POST /api/v1/controls/commands/actions` принимает `{"device_id":"room-01","id":123,"action":"cancel"}` или `action: "retry"`. Требуются same-origin запрос и роль operator/owner. Отмена завершает только ожидающие команды batch-группы указанной команды; уже исполненные цели не откатываются. Повтор разрешён только для завершённой неуспешной группы и создаёт новую ручную группу с новыми id и сроками для неисполненных целей. Для окна устанавливается обычный ручной override. Уже согласованная с фактическим состоянием цель не требует новой команды. Ответ содержит `data.controls` и `data.commands`. Неизвестный id возвращает 404, некорректное действие/состояние — 400, отсутствие прав — 401/403.

`GET /api/v1/controls` дополнен `recent_commands`: все команды последних 20 batch-групп. Интерфейс показывает отдельные результаты целей и частичное выполнение. После завершения без новых pending-команд desired синхронизируется с последним reported. Сбой автоматической команды не запускает бесконечное повторение того же автоматического действия; оператор может повторить его явно. Новое противоположное действие остаётся допустимым.

Отмена команды, уже полученной устройством, не является физическим откатом: до следующей синхронизации устройство могло начать действие. Для изменения реального состояния нужна новая противоположная команда. Обновлённые симуляторы дополнительно проверяют `expires_at` перед исполнением; headless-симулятор прекращает сопровождение истекшей активной команды и останавливает движение окна. Будущая ESP32 должна реализовать аналогичную проверку срока с синхронизированными часами.

Миграция `006_command_lifecycle.sql` сохраняет старые строки, заполняет сроки по их исходному `created_at`, добавляет новые состояния и индекс очистки всех завершённых команд. При обновлении существующей установки примените её перед запуском обновлённого backend. Очистка истории истекает pending-команды до удаления завершённых строк.

## Наружный воздух (M2)

Настройки дополнены `outdoor_policy`: `maxPm25` (по умолчанию 35), `pm25Recovery` (30), `minTemperature` (5 °C), `temperatureRecovery` (7 °C), `filteredIntake` (false), `maxAgeSeconds` (90). PATCH доступен operator/owner и принимает полный объект политики. Порог восстановления PM2.5 должен быть ниже ограничения, температурный — выше; неизвестные поля и неверные типы отклоняются. Настройки сохраняются в PostgreSQL миграцией `007_outdoor_policy.sql`.

| Наружные условия | Окно | Автоматический приток/вытяжка при высоком CO₂ |
|---|---|---|
| Свежие, PM2.5 ниже ограничения, температура выше ограничения | По прежним правилам CO₂ | По прежним правилам CO₂ |
| Повышенный PM2.5, фильтрация не подтверждена | Не открывать автоматически | Не включать автоматически |
| Повышенный PM2.5, фильтрация подтверждена, температура допустима | Закрыть автоматическое окно | Использовать фильтрованный приток и вытяжку |
| Холод либо нет свежих достоверных наружных данных | Закрыть автоматическое окно | Остановить автоматически включённые вентиляторы |

Загрязнение блокирует при PM2.5 ≥ maxPm25, восстанавливается только при PM2.5 < pm25Recovery. Холод блокирует при температуре ≤ minTemperature, восстанавливается только при температуре > temperatureRecovery. Эти признаки сохраняются в состоянии узла и переживают перезапуск. Автоматическое ограничение не отменяет ручной override окна и не выключает вручную включённые вентиляторы. Подтверждённая фильтрация не означает подогрев воздуха: холод блокирует и фильтрованный приток.

Перед обычной остановкой автоматически включённых вентиляторов соблюдается минимальное время вентиляции. Ограничение по холодному/недостоверному воздуху действует сразу. Повторное включение требует восстановления условий и соблюдает lifecycle M1. Старые измерения, поступившие после более свежих, не инициируют команды. Проверка свежести выполняется при запросе состояния и фоново каждые 10 секунд после инициализации API, поэтому прекращение телеметрии не сохраняет прежнее разрешение бесконечно.

`GET /api/v1/controls` дополнен `outdoor_safety`: причины ограничений, разрешённые способы, признаки гистерезиса и времена оценки/измерения. Рекомендация использует тот же результат оценки, что и автоматика. В текущем контракте наружные и внутренние измерения имеют общий timestamp; независимые времена датчиков потребуют расширения device payload.

## Актуальность прогнозов и данных (M3)

Новые прогнозы сохраняют `measurement_id` и `source_timestamp`; рекомендации также связаны с исходным измерением. `GET /api/v1/measurements/latest` выбирает прогноз и рекомендацию именно для последнего измерения, а не независимо последние записи разных таблиц. При неуспешном ML новый measurement сохраняется, его outcome записывается в базе, а старый успешный прогноз не подставляется. `/api/v1/prediction/latest` также возвращает только актуальный связанный прогноз или `data: null`.

`data.diagnostics` содержит:

- `measurement`: missing/fresh/stale, `measuredAt` и `assessedAt`;
- `device`: online/stale/offline по отчётам локального узла;
- `prediction`: ready/pending/insufficient_history/model_untrained/unavailable/error/legacy/stale;
- `predictionMessage`: причина недоступности.

Свежесть измерения проверяется по `DEVICE_HEARTBEAT_TIMEOUT_MS`; timestamp более чем на 5 секунд в будущем считается недостоверным. Прогноз скрывается из текущей карточки, если исходные данные устарели или `target_time` уже прошёл. Поля прогноза дополнены `measurement_id`, `source_timestamp` и `provenance` (linked/legacy/archived). После очистки исходного measurement связь nullable, но доказанный исходный timestamp сохраняется: такие артефакты считаются archived. Старые записи без связи и timestamp остаются legacy; миграция не угадывает их источник по времени.

Миграция `008_prediction_provenance.sql` добавляет nullable-связи и outcome измерения, сохраняя старые записи. ML request timeout охватывает получение заголовков, чтение тела и обработку ответа. Отказ сети, отсутствие модели и malformed response различаются; ошибки не превращаются в фиктивные числовые прогнозы. Для новых точек с недостаточной историей сервис сообщает insufficient_history и не обращается к модели без необходимых признаков.

## M5 — управление моделью

`GET /api/v1/model`: состояние/версия/дата модели, последний фоновый job, предыдущая версия и метрики эксплуатации по источнику и версии. `POST` разрешён только owner с same-origin: `{action:"train", source:"real"|"simulator"|"unknown"}` либо `{action:"rollback"}`. Обучение получает до 5000 доступных точек, запускается в фоне (202), повторный параллельный запуск возвращает 409. Недостаточная история даёт failed job и сохраняет рабочую модель. Backend и ML должны иметь одинаковый отдельный `ML_MANAGEMENT_TOKEN` (минимум 32 символа); браузеру он не передаётся. ML `/management/*` требует этот токен.

Телеметрия поддерживает необязательный `data_source`: real, simulator, unknown. Оба симулятора отправляют simulator. Старые/непомеченные точки остаются unknown; они не объявляются реальными. Источник является заявлением доверенного устройства, а не аппаратной аттестацией. Обучение никогда не смешивает источники. Train/test разделены по времени, обучающие строки с целями в проверочном периоде исключены. MAE/RMSE в отчёте обучения и эксплуатации — разные оценки.

Эксплуатация: один ближайший фактический CO₂ того же источника в пределах ±60 секунд от цели; при равенстве выбирается меньший id. Будущие цели/измерения и legacy без исходного времени исключены. Возвращаются число сопоставлений и MAE/RMSE, только за доступный период сырых данных (retention_hours). Активация проверенного артефакта атомарна; предыдущая модель хранится отдельно. После перезапуска незавершённый job становится failed. Каталог модели должен быть постоянным и доступным для записи.

CLI `ml-service/train.py` также использует блокировку, проверку и атомарную активацию. Если история содержит несколько источников, нужно явно выбрать `--data-source`; смешанная история отклоняется. В отчёте сохраняется источник. Для обучения из интерфейса выбирайте техническую вкладку настроек.

Для признаков нового прогноза используются только точки того же источника. История unknown остаётся отдельной и не используется как тренд реального или синтетического узла.

## M6 — архив и CSV

См. [long-term-history.md](long-term-history.md): `GET /api/v1/history`, периоды 7/30 дней, отдельные источники, предшествующий период, UTC-бакеты, timezone для CSV. Вход обязателен, read доступен всем ролям. `format=csv` возвращает download с единицами. Телеметрия старше финализированного watermark получает 422 `history_finalized`; доступные поздние точки учитываются при пересчёте. Пороги/состояние вентиляции фиксирует сервер, клиент не может подменить эти снимки.

## M7 — журнал и уведомления

Контракты `events` и `notifications`, права, правила эпизодов и защита реквизитов описаны в [notifications.md](notifications.md). Journal доступен вошедшим пользователям, настройки/тест канала — owner. Токен возвращается только как token_configured. Внешняя отправка по умолчанию выключена.


## Телеметрия одной ESP32 (v2)

`POST /api/v1/telemetry` принимает четыре независимо диагностируемых канала, controller health, фактическую обратную связь и результаты команд. Авторизация — device bearer token; предел тела 32 КБ. Новый пакет возвращает 201, идентичный повтор — 200 с исходными id/received_at, конфликт boot_id/sequence — 409. `GET` возвращает последний кадр активного источника с no-store. Формат и достоверность описаны в [telemetry-v2.md](telemetry-v2.md), вымышленный пакет — в [примере](../contracts/telemetry-v2.example.json).

Legacy `POST /api/v1/measurements` сохраняет формат и теперь идемпотентен по содержимому и времени измерений. Необязательный outdoor_timestamp задаёт независимое время наружных данных; старое наружное измерение не становится свежим из-за нового indoor-пакета. Измерения и heartbeat более чем на пять секунд в будущем отклоняются. Повтор не обновляет created_at/время приёма. Полная v2-проекция содержит стабильный ключ пакета; прогноз и рекомендация имеют идемпотентные ключи.

При unknown обратной связи сервер сохраняет последнее известное boolean-состояние, передавая feedback_known отдельно. Такой канал не подтверждает ACK. Открытие окна подтверждается только в заданном крайнем положении с остановленным движением; вращение вентилятора — по согласованным запросу и RPM. Поздний пакет не откатывает текущее состояние. На этапе перехода применить все миграции, включая 012, до запуска нового backend.
