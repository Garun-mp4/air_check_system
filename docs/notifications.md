# События и Telegram

Журнал работает независимо от внешнего канала. В разделе управления вошедший пользователь видит последние 100 событий и отмечает их прочитанными; отметки принадлежат конкретному аккаунту. Хранение — 90 дней.

Условия: длительное превышение текущего порога CO₂ на свежих измерениях; потеря heartbeat; failed/expired последних завершённых команд по цели. Для каждого состояния ведётся постоянный эпизод с длительностью, активностью и временем последнего оповещения. Продолжающийся эпизод создаёт одно сообщение. Подавление ограничивает новые эпизоды после быстрого восстановления. Устаревший CO₂ не означает нормальный воздух и не порождает ложное восстановление. После разрыва наблюдений начинается новый неанонсированный dwell. Восстановление команды фиксируется после успешной последующей команды той же цели; pending/cancelled не заменяют подтверждённое восстановление.

Настройки доступны owner в технической вкладке: dwell CO₂/потери связи (1–86400 секунд), подавление повторов (0–86400), выбранный числовой Chat ID и токен бота. Внешняя отправка выключена по умолчанию. Для её включения нужны сохранённые реквизиты. При изменении чата/отключении ожидающие обычные сообщения отменяются. Журнал продолжает работать.

Токен шифруется AES-256-GCM со случайным nonce. Ключ получается из `NOTIFICATION_ENCRYPTION_KEY` (если задан) либо отдельной derivation `BETTER_AUTH_SECRET`; минимум 32 символа. API возвращает только token_configured. Значение никогда не загружается обратно в поле, не выдаётся в событиях и не логируется. После смены ключа нужно повторно сохранить токен. Рекомендуется отдельный стабильный ключ для production; Compose передаёт его backend. Новый токен не сохраняется в git/.env.example.

«Отправить тест в выбранный чат» явно ставит тестовое сообщение для сохранённого Chat ID; сервер отклоняет другой/неуказанный чат. Тест доступен независимо от общего включения внешних уведомлений, поскольку отправка подтверждена отдельным действием владельца. Результат отображается в журнале. Без этих действий реальная тестовая отправка не производится.

Доставка имеет состояния pending/sending/sent/failed/disabled, максимум три попытки и задержки 30/60 секунд. HTTP и чтение ответа ограничены 5 секундами. Worker опрашивает каждые 10 секунд, claim использует SKIP LOCKED и lease 30 секунд, восстанавливает прерванные попытки; после третьей ошибки задача окончательно failed. Ошибка сохраняет журнал и не блокирует измерения/управление. Результат sent означает принятие Telegram, а не прочтение адресатом. При сбое между принятием сообщения и записью результата возможен повтор; Telegram sendMessage не предоставляет транзакционную идемпотентность.

API: `GET /api/v1/events` (вход), `PATCH {id}` (own read mark, same-origin); `GET/PATCH /api/v1/notifications` (owner, PATCH same-origin); `POST {chat_id}` — явный тест owner. Поля PATCH: enabled, co2_duration_seconds, offline_duration_seconds, suppression_seconds, telegram_chat_id, необязательные bot_token или clear_token. Неизвестные поля отклоняются; ciphertext не принимается.

Автотесты используют локальный контролируемый HTTP-транспорт. Только стенд с `AIRCHECK_E2E=1` и loopback `AIRCHECK_TELEGRAM_TEST_URL` может направить запрос в него; production использует api.telegram.org. Стенд применяет вымышленный токен/чат, не пишет URL с токеном в логи и не обращается в настоящий Telegram.

Worker и задачи очистки/автоматики запускаются через Next instrumentation при старте сервера с PostgreSQL-конфигурацией. Поэтому после перезапуска backend контроль связи продолжается даже при выключенном устройстве и закрытой панели. GET journal дополнительно актуализирует условия.
