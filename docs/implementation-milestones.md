# План развития AirCheck

Milestones расположены от наиболее приоритетных к менее приоритетным. Каждый milestone — одна законченная задача. Реализация выполнена последовательно; результаты и проверки записаны в [отчётах](testing/README.md).

## Правила выполнения

- Реализовывать строго последовательно: M1 → M2 → M3 → M4 → M5 → M6 → M7.
- Не начинать следующий milestone, пока текущий не реализован полностью, не проверен и не соответствует всем критериям готовности.
- Внутри milestone завершать всю цепочку: схема данных и миграции, серверная логика, API, интерфейс, тесты и документация — в той мере, в которой задача затрагивает эти части.
- Сохранять совместимость с существующими данными и контрактами устройств. Изменения контрактов документировать; миграции проверять как на чистой, так и на существующей базе.
- Для изменений интерфейса соблюдать `DESIGN-cal.md` и существующие компоненты; проверять адаптивность, клавиатурное управление и состояния загрузки, ошибки и отсутствия данных.
- Не включать в milestone несвязанные улучшения. Если обнаружена блокирующая проблема, устранить её в текущем milestone и повторить затронутые проверки.
- По завершении фиксировать результат и проверки в коротком отчёте. Провал обязательной проверки или незавершённый критерий готовности блокирует переход дальше.

## M1. Надёжный жизненный цикл команд управления

**Задача:** исключить исполнение устаревших команд и сделать результат управления однозначным для пользователя.

### Объём реализации

- Расширить текущие состояния `pending` и `applied` состояниями `failed`, `cancelled` и `expired`; определить допустимые переходы.
- Добавить срок действия команды, время завершения и причину неуспеха. Определить отдельные правила для ручных и автоматических команд.
- Истекшую или отменённую команду исключать из выдачи устройству; поздний ACK не должен возвращать её в состояние `applied`.
- При новой противоположной команде отменять устаревшую ожидающую команду для той же цели. Для вентиляционных batch-команд определить согласованность результатов и отображение частичного выполнения.
- Сохранять проверку соответствия ACK фактическому состоянию. Старым устройствам без сообщения об ошибке оставить совместимый способ подтверждения; явный отказ устройства поддержать как расширение контракта.
- Добавить оператору отмену ожидающей команды и явное повторное создание команды после ошибки; не вводить бесконечные автоматические повторы.
- Показать в интерфейсе состояние команды и причину проблемы, согласовать desired/actual state после отмены и истечения.
- Обновить миграции, правила очистки завершённых команд, API и документацию симулятора.

### Критерии готовности

- После длительного отключения устройство не получает истекшие или отменённые команды.
- Конкурентные запросы, повторный ACK, поздний ACK и противоположные команды дают предсказуемый результат без дубликатов и недопустимых переходов.
- Проверены успешное выполнение, отказ устройства, истечение, отмена и частичное выполнение batch-команды.
- Миграция сохраняет существующие команды; сервер, PostgreSQL и симулятор проходят соответствующие интеграционные проверки.
- Пользователь видит, исполнена ли команда, и может отменить ожидающую или повторить неуспешную команду в пределах своих прав.

**После завершения:** перейти к M2.

## M2. Автоматика с учётом наружного воздуха

**Задача:** учитывать наружный PM2.5 и температуру при выборе способа проветривания.

### Объём реализации

- Определить таблицу решений для сочетаний текущего/прогнозируемого CO₂, наружного PM2.5, температуры и состояния оборудования.
- Различать открытие окна и работу вентиляции. Возможность безопасного фильтрованного притока определять по явно заданным возможностям установки, а не предполагать наличие эффективного фильтра.
- Добавить настройки ограничений, приоритетов и условий восстановления; использовать раздельные пороги включения/выключения и минимальную длительность режима для защиты от частых переключений.
- Задать поведение при отсутствии или устаревании наружных данных. Сохранить ручной режим окна и ограничения из M1.
- Согласовать рекомендацию и автоматическую команду: интерфейс должен объяснять, какое условие определило действие или запретило его.
- Добавить сценарии загрязнённого и холодного наружного воздуха в симулятор и обновить документацию правил.

### Критерии готовности

- Проверены конфликтующие условия: высокий CO₂ одновременно с загрязнённым или холодным наружным воздухом, а также отсутствие свежих наружных данных.
- Поведение соответствует таблице решений; рекомендация не противоречит командам автоматики.
- На колебаниях около порога нет частых переключений; ручной режим и сроки действия команд соблюдаются.
- Новые настройки валидируются, сохраняются и доступны только пользователям с соответствующими правами.

**После завершения:** перейти к M3.

## M3. Актуальность измерений и прогнозов

**Задача:** показывать согласованное состояние данных, связи и ML, исключив представление старого прогноза как текущего.

### Объём реализации

- Связать прогноз с исходным измерением и временем его построения; отдельно показывать целевое время прогноза.
- Возвращать в dashboard/API статус свежести измерений, связи с устройством и доступности прогноза для текущего измерения.
- При отказе ML не подставлять последний успешный прогноз в карточку текущего измерения. При необходимости показывать его отдельно с явной отметкой времени.
- Различать состояния: нет данных, данные актуальны, данные устарели, устройство отключено, модель не обучена, ошибка ML и прогноз доступен.
- Распространить timeout ML-клиента на чтение тела ответа, а не только получение HTTP-заголовков; измерения должны сохраняться и при отказе ML.
- Добавить понятные статусы и время последней синхронизации, не нарушая работающие рекомендации по текущим измерениям.
- Для старых прогнозов без доказуемой связи с измерением использовать явный legacy-статус, не создавать связь по догадке.

### Критерии готовности

- После нового измерения и отказа ML старый прогноз не выглядит прогнозом по новым данным.
- Проверены задержка тела HTTP-ответа, недоступность ML, отсутствующая модель, потеря связи и последующее восстановление.
- API и интерфейс согласованно сообщают время, свежесть и причину недоступности; новая телеметрия сохраняется независимо от результата ML.
- Миграция существующих прогнозов не теряет данные и не приписывает им неподтверждённые связи.

**После завершения:** перейти к M4.

## M4. Браузерная проверка основных пользовательских сценариев

**Задача:** добавить воспроизводимый E2E-набор для настоящего браузера и реальных сервисов.

### Объём реализации

- Подготовить браузерный тестовый стенд с изолированной PostgreSQL, тестовыми аккаунтами, ML и симулятором; не использовать рабочие данные и существующие volumes.
- Проверить вход, выход, cookie-сессию, роли и запреты на недоступные действия через реальную интеграцию Better Auth.
- Проверить ручную команду до фактического подтверждения, отмену/истечение из M1, изменение настроек и статусы из M3.
- Проверить загрузку 3D-сцены, получение состояния и ключевое pointer-взаимодействие в браузере с WebGL.
- Проверить основные desktop/mobile размеры и клавиатурную навигацию. Не заменять функциональные проверки только сравнением скриншотов.
- Добавить команду запуска и CI-проверку с отчётами, trace и скриншотами ошибок; гарантировать очистку только созданных тестом ресурсов.

### Критерии готовности

- Тесты проходят с чистой базой и повторно, без зависимости от предыдущего запуска или внешних аккаунтов.
- Отказ авторизации, неправильные права и отсутствие подтверждения команды действительно приводят к провалу соответствующего теста.
- WebGL-сценарий выполняется, а не молча пропускается. Поддерживаемая среда его запуска документирована.
- CI запускает согласованный обязательный набор, сохраняет диагностику ошибок и не оставляет тестовые контейнеры или данные.

**После завершения:** перейти к M5.

## M5. Управление и оценка ML-модели

**Задача:** дать владельцу возможность обучать модель и оценивать её качество на накопленной истории.

### Объём реализации

- Показать состояние модели, версию, дату обучения, диапазон данных, число обучающих строк и метрики MAE/RMSE.
- Добавить запуск обучения владельцем через фоновую задачу с состояниями ожидания, выполнения, успеха и ошибки; запретить параллельные запуски.
- Проверять достаточность истории и целостность признаков, сохранять временное разделение train/test без утечки будущих данных.
- Сохранять работающую модель при неуспешном обучении. Активировать проверенный новый артефакт атомарно; предусмотреть возврат к предыдущей версии.
- Сопоставлять прогноз с фактическим CO₂ через 15 минут по заданному допустимому временному отклонению. Различать метрики обучения и качество прогнозов при эксплуатации.
- Отделять синтетические данные симулятора от реальных при оценке качества; явно подписывать источник данных в интерфейсе.

### Критерии готовности

- Владелец запускает обучение из панели и видит результат; остальные роли не могут его запускать.
- Недостаточная история, ошибка обучения и повторный запрос обрабатываются без потери действующей модели.
- После успешного обучения сервис использует новую версию; возврат к предыдущей версии проверен.
- Метрики эксплуатации считают только прогнозы с подходящим фактическим измерением и показывают число сопоставлений.
- Браузерный набор из M4 дополнен сценарием обучения и обновления статуса модели.

**После завершения:** перейти к M6.

## M6. Долгосрочная история и экспорт

**Задача:** сохранить полезную статистику за неделю и месяц без неограниченного роста сырых данных.

### Объём реализации

- Сохранить текущую политику хранения сырых измерений и добавить отдельные агрегаты для долгосрочной истории.
- До удаления сырых данных формировать агрегаты: средние/минимальные/максимальные показатели, покрытие измерениями, длительность превышений порогов и проветриваний.
- Определить правила для пропусков телеметрии, поздних измерений, смены порогов и часовых поясов. Не считать отсутствие данных нормальным состоянием.
- Добавить периоды 7 и 30 дней, сводку и сравнение периодов в интерфейсе.
- Добавить CSV-экспорт с выбором периода, единицами измерения, временной зоной, правами доступа и ограничением размера ответа.
- Сделать агрегацию повторяемой без дублирования; не восстанавливать уже удалённую историю вымышленными значениями.

### Критерии готовности

- Очистка сырых измерений не уничтожает рассчитанную долгосрочную статистику.
- Повторная агрегация и перезапуск не меняют результат при неизменных исходных данных.
- Проверены пропуски, поздние записи, границы суток и смена порогов; интерфейс показывает неполное покрытие.
- Графики и экспорт согласованы с базой; запросы за месяц выполняются по агрегатам с подходящими индексами.
- Пользователь может выгрузить выбранный период; браузерные проверки охватывают новый период истории и экспорт.

**После завершения:** перейти к M7.

## M7. Уведомления о важных событиях

**Задача:** сообщать о проблемах без необходимости постоянно держать панель открытой.

### Объём реализации

- Создать журнал событий: длительное превышение CO₂, потеря связи, неисполненная команда и восстановление нормального состояния.
- Добавить настройки длительности нарушения, периода подавления повторов и включения уведомлений; одно продолжающееся нарушение не должно порождать поток одинаковых сообщений.
- Добавить просмотр событий и отметку прочтения в панели.
- Реализовать один внешний канал — Telegram. Web Push оставить отдельной будущей задачей, чтобы не расширять объём milestone.
- Настройку канала разрешить владельцу; реквизиты хранить безопасно, не возвращать токен в API и не писать его в логи. Без настроенного канала журнал должен работать самостоятельно.
- Добавить проверку подключения, ограниченные повторы доставки и понятный статус ошибки; сбой уведомлений не должен блокировать телеметрию или управление.

### Критерии готовности

- Для каждого поддерживаемого события проверены возникновение, подавление повторов и восстановление.
- При временном отключении Telegram событие остаётся в журнале, а доставка повторяется в заданных пределах без бесконечной очереди.
- Тесты доставки используют контролируемый транспорт; реальная отправка тестового сообщения выполняется только в явно выбранный владельцем чат.
- Права доступа и защита реквизитов проверены; браузерный набор покрывает журнал и настройки канала.

**После завершения:** план завершён; следующие задачи определяются по результатам эксплуатации.

## Обязательная проверка завершения каждого milestone

1. Все критерии готовности текущего milestone выполнены и подтверждены проверками.
2. Пройдены существующие frontend/Python тесты, typecheck и production build; новые сценарии покрыты соответствующими тестами.
3. При изменениях БД пройдены PostgreSQL-тесты и проверка обновления существующей схемы; при изменениях межсервисных контрактов — затронутые интеграционные/E2E-проверки.
4. Начиная с M4 пройден обязательный браузерный E2E-набор.
5. Проверены запуск сервисов и затронутый пользовательский сценарий на работающем приложении.
6. Обновлены документация API, настройки и инструкции запуска, если они изменились.
7. Записан краткий отчёт: что реализовано, какие проверки выполнены, какие ограничения остались. Незавершённая часть текущей задачи не переносится в следующий milestone ради формального завершения.
